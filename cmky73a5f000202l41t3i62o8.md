## Introduction: Why Wireshark Matters in Cybersecurity

Wireshark is one of the most powerful tools in networking and cybersecurity. It lets you **capture and analyze network traffic** in real time, basically showing you what your computer is “saying” on the internet.

If you’re preparing for a cybersecurity internship (SOC / VAPT / Network Security), Wireshark is a **must-have skill** because it helps you:

* troubleshoot network issues
    
* investigate suspicious activity
    
* understand protocols deeply
    
* Detect attacks like scanning, spoofing, and malware communication
    

**In simple words:**  
Wireshark is like **CCTV for network traffic**.  
You can’t stop what already happened, but you can **see everything clearly**.

---

## What is Wireshark?

Wireshark is a **packet analyzer**.

A *packet* is a small piece of data that moves across a network. Every time you:

* open Instagram
    
* Log in to a website
    
* watch YouTube
    
* Send a message on WhatsApp Web  
    Your device sends and receives packets.
    

Wireshark captures these packets and shows:

* **source IP**
    
* **destination IP**
    
* **protocol used** (TCP, UDP, DNS, HTTP, TLS)
    
* packet timing, size, and errors
    

### Relatable Example: “Courier Delivery”

Imagine you ordered a phone online.

* The **website** sends your package
    
* The package travels through multiple delivery hubs
    
* It reaches your home
    

Packets are like those **delivery parcels**, and Wireshark is the tool that lets you **track each parcel**:  
where it came from, where it went, and what happened in between.

## Why Cybersecurity People Use Wireshark

Wireshark helps in both **defensive** and **offensive** security.

### Defensive (SOC / Blue Team)

* Detect suspicious connections
    
* Investigate malware traffic
    
* Analyze data exfiltration patterns
    
* Find compromised devices talking to unknown IPs
    

### Offensive (VAPT / Red Team)

* Analyze app behavior
    
* Debug payload delivery
    
* Identify insecure protocols
    
* Find misconfigurations and exposed services

## Installing Wireshark (Quick Setup)

### Windows

* Install Wireshark + **Npcap**
    
* Npcap is required to capture packets
    

### Linux

Use your distro package manager (Ubuntu/Debian example):

```plaintext
sudo apt update
sudo apt install wireshark
```

### macOS

Install via Homebrew:

```plaintext
brew install --cask wireshark
```

📌 **Permission Tip (Linux/macOS):**  
If you can’t capture traffic, you may need admin/root permissions.

## Capture vs Display Filters (Important!)

### Capture Filters

Applied **before capturing** → saves only what you want  
Example: capture only DNS

```plaintext
port 53
```

### Display Filters

Applied **after capturing** → show/hide results  
Example:

```plaintext
dns
```

**Relatable example:**  
Capture filter = choosing which CCTV cameras to record  
Display filter = searching footage after recording

## Beginner Concepts You Must Understand (with Examples)

### 1) DNS (Domain Name System)

**DNS is the Internet’s phonebook.**

You type: [`google.com`](http://google.com)  
Computer needs: `142.250.xx.xx`

So DNS converts:  
**Name → IP**

![](https://cdn.hashnode.com/res/hashnode/image/upload/v1769602870559/43d7d971-969a-4ae4-9965-78c3eb7fb2c7.png align="center")

Wireshark filter:

```plaintext
dns
```

Useful DNS filters:

```plaintext
dns.qry.name contains "google"
```

---

### 2) TCP vs UDP (Delivery Styles)

**TCP = reliable delivery**  
Like sending a courier with tracking + signature.

**UDP = fast delivery**  
Like shouting information on a walkie-talkie (no confirmation).

Wireshark filters:

```plaintext
tcp
udp
```

---

### 3) TLS (Secure Tunnel / Lock System)

TLS is what makes **HTTPS secure**.

Without TLS:  
Your password is like writing it on a postcard 🧾  
Anyone can read it.

With TLS:  
Your password is inside a locked box 🔒  
Only the website can open it.

Wireshark filter:

```plaintext
tls
```

📌 Even if traffic is encrypted, Wireshark still shows:

* Which IP did you connect to
    
* TLS handshake details
    
* certificate information
    
* domain name via SNI (often)

## Wireshark Display Filters Cheat Sheet (Daily Use)

### Find traffic for one IP

```plaintext
ip.addr == 192.168.1.10
```

### Find traffic for one port

```plaintext
tcp.port == 443
```

### HTTP requests

```plaintext
http.request
```

### DNS only

```plaintext
dns
```

### Only SYN packets (scan/connection start)

```plaintext
tcp.flags.syn == 1 && tcp.flags.ack == 0
```

### TCP resets

```plaintext
tcp.flags.reset == 1
```

* view HTTP requests/responses
    
* analyze plaintext protocols

## Advanced Wireshark Topics (Intern-Ready)

### 1) TCP Handshake & Connection Analysis

TCP 3-way handshake:

1. SYN
    
2. SYN-ACK
    
3. ACK
    

Wireshark filter:

```plaintext
tcp.flags.syn == 1
```

If you see many SYN but no SYN-ACK:

* firewall blocking
    
* host down
    
* packet drops
    

---

### 2) Retransmissions & Packet Loss

Wireshark often marks:

* Retransmission
    
* Duplicate ACK
    
* Out-of-order packets
    

This indicates:

* network congestion
    
* packet loss
    
* unstable Wi-Fi
    

Filter sometimes used:

```plaintext
tcp.analysis.retransmission
```

---

### 3) ARP Spoofing / MITM basics

ARP maps:  
IP → MAC address in the local network.

If an attacker performs ARP spoofing, you may see:

* Repeated ARP replies
    
* One MAC claiming multiple IPs
    

Filter:

```plaintext
arp
```

---

### 4) DNS Tunneling Suspicion (Basic Detection)

DNS tunneling often has:

* very long subdomains
    
* high frequency DNS queries
    
* weird patterns
    

Filter:

```plaintext
dns
```

Look for:

* unusually long [`dns.qry.name`](http://dns.qry.name)
    
* too many TXT queries

## Best Practices for Professionals

* Always save files as `.pcapng`
    
* Use the **time display format** properly
    
* Add columns (SNI, ports, TCP flags)
    
* Use “Protocol Hierarchy” for an overview
    

Go to:  
**Statistics → Protocol Hierarchy**

## Common Wireshark Mistakes (Avoid These)

* Capturing on the wrong interface
    
* Not using filters → drowning in packets
    
* Ignoring timestamps
    
* Confusing capture filter vs display filter
    
* Expecting to read HTTPS content (it’s encrypted)
